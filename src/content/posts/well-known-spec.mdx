## Abstract

There is no widely-adopted convention for publishing versioned specifications on a website. OpenAPI documents live wherever the publisher feels like ([open issues since 2019](https://github.com/OAI/OpenAPI-Specification/issues/1851)); JSON Schemas live wherever the `$id` says; community conventions live in blog posts or GitHub READMEs, sometimes with version-pinned URLs and sometimes not. This document proposes a small, opt-in convention: publish versioned specifications as JSON Schema documents under `/.well-known/spec/{name}/v{x.y.z}.json`, with an additional latest-version alias at `/.well-known/spec/{name}.json`.

The convention is recursive: this specification is itself published at the URLs it specifies, in the format it specifies, and validates against itself. The canonical machine-readable artifact is:

```
https://ben.abbitt.me/.well-known/spec/well-known-spec/v0.1.0.json
```

Publishing is opt-in. Nothing here mandates that any host publish anything.

## 1. Introduction

When OpenAPI publishers want consumers to find their specification documents at a predictable URL, they reinvent the choice — `/openapi.json`, `/api-docs`, `/swagger.json`, `/.well-known/openapi`, `/v1/openapi.json`. The OpenAPI community has been [discussing a standard well-known location since 2019](https://github.com/OAI/OpenAPI-Specification/issues/1851) without resolution. When a community spec like Semantic Versioning has a stable URL, it lives on a project-specific domain (`semver.org`) without a generalizable convention for any other community spec to follow. When IETF drafts about HTTP versioning ([the expired draft-nottingham-http-over-version](https://datatracker.ietf.org/doc/html/draft-nottingham-http-over-version-00), [the expired draft-claise-semver](https://datatracker.ietf.org/doc/html/draft-claise-semver-02)) need permanent URLs, they get them from the IETF datatracker, but only after the months-long Internet-Draft process.

What is missing is a casual, low-ceremony pattern for any individual or small project to publish a versioned spec at a URL that:

- Identifies the host that publishes it (different hosts may publish different specs of the same name).
- Identifies the spec name unambiguously.
- Identifies the exact version of the spec, immutable and stable.
- Optionally provides a "give me the latest" alias.
- Is discoverable by convention without registration.
- Doesn't pretend to be more authoritative than a community proposal.

This document proposes such a pattern: `/.well-known/spec/{name}/v{x.y.z}.json` for the versioned URL and `/.well-known/spec/{name}.json` for the latest alias. The choice of `.well-known/` is grounded in [RFC 8615](https://datatracker.ietf.org/doc/html/rfc8615), which reserves the path prefix for site-wide metadata. No new IANA registration is required, because the spec documents are leaf files under `.well-known/`, not new well-known URI suffixes.

The form of the spec document is also opinionated: it MUST be a JSON Schema (draft 2020-12), so that tooling can validate documents claiming conformance to it, and so that "the spec" and "the validation schema" are the same artifact.

## 2. Conventions and Terminology

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as described in [RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119) and [RFC 8174](https://datatracker.ietf.org/doc/html/rfc8174), but only when they appear in all-uppercase, and **only as constraints on spec documents that opt in to this convention**. Nothing in this document requires any host to publish a spec.

The term *spec document* refers to a JSON Schema published at a `/.well-known/spec/...` URL as defined by this convention.

The term *latest alias* refers to the bare-name URL `/.well-known/spec/{name}.json` (without the version segment) serving the most recent published version's content.

## 3. Optionality and Scope

This convention is opt-in. Specifically:

- A host is **NOT REQUIRED** to publish any spec documents. The absence of `/.well-known/spec/*` is conformant.
- A host that publishes a spec document is **NOT REQUIRED** to also publish a latest alias.
- A host that publishes multiple specs MAY publish them in any subset of the namespaces under `/.well-known/spec/`.

The convention's MUST and SHOULD language applies only to documents that exist. Hosts publishing nothing are conformant. Documents published at `/.well-known/spec/{name}/v{x.y.z}.json` MUST be shaped per §5. Latest aliases MUST follow §4.

This convention is unrelated to whether the *thing* a spec describes (a manifest format, a header, a protocol) is opt-in. That is the individual spec's concern. This convention concerns only where and how *spec documents themselves* are published.

## 4. URL Convention

### 4.1. Canonical Versioned URL

A conforming spec document for a spec named `{name}` at version `{x.y.z}` MUST be served at:

```
https://{host}/.well-known/spec/{name}/v{x.y.z}.json
```

where:

- `{host}` is the publishing origin (scheme, host, and optional port per [RFC 6454](https://datatracker.ietf.org/doc/html/rfc6454)).
- `{name}` is the spec name. It MUST match the pattern `^[a-z][a-z0-9-]*$` (lowercase kebab-case, starting with a letter).
- `{x.y.z}` is the spec version, a [semver 2.0.0](https://semver.org/spec/v2.0.0.html) string. The leading `v` is REQUIRED.

The canonical URL MUST be served with `Content-Type: application/json` or, RECOMMENDED, `Content-Type: application/schema+json`.

The canonical URL is immutable. Once published at a given version, the content at that URL MUST NOT change. Editorial PATCH-level changes that do not alter the schema's normative effect (typo fixes in `description` fields) MAY be made without a version bump, but the publisher SHOULD prefer a PATCH version bump.

### 4.2. Latest-Version Alias

A host SHOULD also serve the latest published version of each spec at the bare-name URL:

```
https://{host}/.well-known/spec/{name}.json
```

The latest alias serves the same content as the highest-precedence semver of all the published versions of `{name}`. Precedence is per [semver 2.0.0 §11](https://semver.org/spec/v2.0.0.html#spec-item-11) (prerelease versions have lower precedence than the corresponding normal version).

The latest alias is mutable. Consumers MUST NOT pin references to the latest alias if they require a specific version's behavior.

The latest alias MUST be served with the same media type as the canonical versioned URL it currently points to.

### 4.3. Cache-Control

Both the canonical versioned URL and the latest alias SHOULD be served with appropriate Cache-Control headers:

- Canonical versioned URL: Long `max-age` is appropriate; the content is immutable. RECOMMENDED `Cache-Control: public, max-age=31536000, immutable` (one year, immutable).
- Latest alias: Short `max-age` or `no-cache` is appropriate; the content changes when new versions are published. RECOMMENDED `Cache-Control: no-cache` or `max-age` under 300.

## 5. Spec Document Format

### 5.1. JSON Schema Requirement

A conforming spec document MUST be a JSON Schema, by default of dialect [draft 2020-12](https://json-schema.org/draft/2020-12/schema). Future spec versions of `well-known-spec` MAY relax this to additional dialects.

### 5.2. Required Top-Level Fields

A conforming spec document MUST have the following top-level fields:

- `$schema` (string, URI) — MUST identify the JSON Schema dialect. RECOMMENDED: `"https://json-schema.org/draft/2020-12/schema"`.
- `$id` (string, URI) — MUST be the canonical versioned URL of the spec document. MUST NOT be the latest-alias URL.
- `title` (string, non-empty) — Human-readable name including the version, e.g. `"deployment-version v0.1.0"`.

The document SHOULD also include a `description` field with a one-paragraph abstract that includes the URL of any narrative companion document.

The document MAY include any other JSON Schema keywords as needed to describe the structure it validates.

### 5.3. What This Convention Does Not Require

A conforming spec document is **NOT REQUIRED** to:

- Carry custom metadata fields (`x-spec-name`, `x-spec-version`, etc.). The name and version are derived from the URL. The status (draft / stable / deprecated) is implicit in the semver: `0.x.y` is draft by convention; `1.0.0` and later are stable; deprecation is communicated by publishing a new major version and updating the latest alias.
- Reference a particular IANA registration. No registration is required.
- Use a particular license. Publishers SHOULD declare a license in the narrative companion document.

The deliberate minimalism reflects that everything else is already either implicit in the URL or appropriately handled by the narrative companion document. The JSON Schema is the contract; words are words.

## 6. Self-Validation

`well-known-spec` v0.1.0 is itself a JSON Schema that validates spec documents conforming to `well-known-spec`. Because `well-known-spec` v0.1.0 is itself published as a `well-known-spec`-conforming document, it must validate against itself. It does.

A tool that wants to verify a spec document at `/.well-known/spec/{name}/v{x.y.z}.json` is conformant can:

1. Fetch `well-known-spec` from the publishing host at [`/.well-known/spec/well-known-spec/v0.1.0.json`](/.well-known/spec/well-known-spec/v0.1.0.json) (or [`/.well-known/spec/well-known-spec.json`](/.well-known/spec/well-known-spec.json) for the latest), OR from a known reference host such as [`https://ben.abbitt.me/.well-known/spec/well-known-spec/v0.1.0.json`](https://ben.abbitt.me/.well-known/spec/well-known-spec/v0.1.0.json).
2. Validate the candidate spec document against that schema.

Multiple hosts MAY publish their own copies of `well-known-spec`. Hosts SHOULD use the same content for the same version; this is by convention, not by enforcement.

## 7. Versioning of This Spec

This spec is itself versioned per [semver 2.0.0](https://semver.org/spec/v2.0.0.html).

- **MAJOR** version bumps signal changes that invalidate existing spec documents — for instance, removing a required field, repurposing a field name, or changing the meaning of a required field.
- **MINOR** version bumps signal additions that do not invalidate existing spec documents — for instance, allowing additional JSON Schema dialects, adding OPTIONAL fields.
- **PATCH** version bumps signal clarifications and typo fixes with no normative change.

A spec document MAY identify the version of `well-known-spec` it conforms to in its `description`. There is no required field for this; consumers can verify conformance against any version of `well-known-spec` they consider appropriate.

## 8. Security Considerations

The security surface of this convention is small.

Publishing spec documents at predictable URLs is a discoverability feature, not a security concern. The spec documents themselves carry no operational data — they are JSON Schemas describing other data. A consumer fetching `https://example.com/.well-known/spec/deployment-version/v0.1.0.json` learns that this host publishes the `deployment-version` convention; whether they fetch a corresponding manifest at `/.well-known/deployment-version.json` is a separate question with separate security considerations (see [`deployment-version` §9](/posts/deployment-version/)).

Hosts publishing spec documents MUST ensure those documents are immutable at their canonical versioned URL. A host that publishes content at `/.well-known/spec/{name}/v0.1.0.json` and later silently replaces it with different content has broken the contract that pinned references depend on. Such a host harms consumers who pinned to the URL.

The latest alias is explicitly mutable; consumers who follow it accept that.

Cross-host references to spec documents may be subject to TLS, DNS, and routing trust. Consumers validating against a spec document at a remote URL SHOULD use HTTPS and SHOULD pin their dependency to a specific version (the canonical versioned URL), not the latest alias, when they require deterministic validation behavior.

## 9. Discoverability

This convention is discoverable in the way [RFC 8615](https://datatracker.ietf.org/doc/html/rfc8615) intends. A consumer aware of `well-known-spec` and the name of a spec they want can:

1. Probe `https://{host}/.well-known/spec/{name}.json` for the latest.
2. Probe `https://{host}/.well-known/spec/{name}/v{x.y.z}.json` for a specific version.
3. Receive a 404 if the host has not published the spec.

The 404 is informative. It says "this host does not publish this spec," and the consumer can proceed accordingly.

This convention does NOT specify a discovery endpoint listing all specs a host publishes. A host that wants to advertise its full spec catalog MAY publish a manifest at `/.well-known/specs.json` or some similar location, but the format and existence of such a manifest are out of scope for this version of `well-known-spec`. Future versions MAY add this.

Crawlers and search engines generally do not index `.well-known/` paths by default. Hosts that want their spec documents to be discoverable to general search MAY explicitly link them from publicly-indexable pages.

## 10. IANA Considerations

This convention, as currently published, is **not fully conformant with [RFC 8615](https://datatracker.ietf.org/doc/html/rfc8615)'s registration requirements.** RFC 8615 §3 requires that any name used as a well-known URI suffix MUST be registered with IANA via the Expert Review process. The `spec` suffix used by this convention is unregistered.

This places the convention in the same category as a substantial fraction of `/.well-known/` usage in the wild: practical, recognizable, technically unregistered. Provisional registration of `spec` as a well-known URI suffix is suggested as future work and would not require advancement to RFC status.

The convention treats the segment immediately after `spec` (the spec name, e.g. `deployment-version`) as a sub-path under the registered suffix, not as its own registered suffix. RFC 8615's ABNF allows multi-segment URLs under a registered prefix (see [RFC 8615 §3](https://datatracker.ietf.org/doc/html/rfc8615#section-3); existing precedent: `/.well-known/acme-challenge/{token}` from [RFC 8555](https://datatracker.ietf.org/doc/html/rfc8555)). Registration of `spec` would therefore suffice for any number of specs published under it.

Adopters concerned about strict RFC 8615 conformance are advised to await registration (preferred) or to deploy a host-specific variant under a known-conformant suffix.

The `application/json` and `application/schema+json` media types are used unchanged. The convention does not define a new media type.

```json
  "title": "deployment-version v0.1.0",
  "description": "Manifest schema for HTTP-served deployments exposing deploy/build version. Narrative at https://ben.abbitt.me/posts/deployment-version/.",
  "type": "object",
  "required": ["spec", "elements"],
  "properties": { /* full schema elided */ },
  "$defs": { /* element and elementsArray definitions */ }
}
```

## Appendix B: Implementation Patterns

### B.1. Astro Static Endpoint

```ts
// src/pages/.well-known/spec/my-spec/v0.1.0.json.ts
import schema from "@/lib/specs/my-spec-v0.1.0.json";

export async function GET() {
  return new Response(JSON.stringify(schema, null, 2), {
    headers: {
      "Content-Type": "application/schema+json",
      "Cache-Control": "public, max-age=31536000, immutable",
    },
  });
}
```

For the latest alias, a second endpoint at `src/pages/.well-known/spec/my-spec.json.ts` imports the same JSON, served with a short cache lifetime.

### B.2. nginx Static

```nginx
location /.well-known/spec/my-spec/v0.1.0.json {
  add_header Content-Type "application/schema+json";
  add_header Cache-Control "public, max-age=31536000, immutable";
  alias /var/www/specs/my-spec-v0.1.0.json;
}

location = /.well-known/spec/my-spec.json {
  add_header Content-Type "application/schema+json";
  add_header Cache-Control "no-cache";
  alias /var/www/specs/my-spec-latest.json;
}
```

### B.3. GitHub Pages and Other Static Hosts

GitHub Pages does not allow custom `Content-Type` or `Cache-Control` headers. Static spec files are served with the default `application/json` Content-Type (since the file extension is `.json`) and GitHub's default cache behavior. The convention is satisfied; the headers are degraded.

A site can place files directly at the paths:

```
public/.well-known/spec/my-spec/v0.1.0.json
public/.well-known/spec/my-spec.json
```

and these will be served at the corresponding URLs.
